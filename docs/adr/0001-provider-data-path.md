# ADR 0001 — ESPN + Sleeper data path

Status: accepted (in progress)
Date: 2026-08-30

## Context

Sideline is a local companion. It needs live-enough fantasy scores with no backend. Sleeper is official HTTP. ESPN is unofficial, cookie-gated, personal use only. This ADR records what exists, what we will not do, and the poller changes that make live data actually live.

## Decision: do not scrape ESPN HTML

There is **no official ESPN Fantasy API**. There **is** a JSON API that fantasy.espn.com itself uses. Sideline already calls it:

`https://lm-api-reads.fantasy.espn.com/apis/v3/games/ffl/seasons/{year}/segments/0/leagues/{id}?view=…`

HTML scraping (scoreboard pages, FantasyCast DOM) is slower, more brittle, and worse than this. We will not add a scraper. League JSON may arrive as `{ data|payload|league|result|body: { schedule, teams, … } }`; matchup, overlay, team, tape, and fan parsers unwrap that shell so a shape change cannot stall HUD. `schedule.games` / `schedule.matchups` / a matchup-id map of `{ home, away }` rows parse the same as a schedule array. Compact `totalPointsLive` / `liveScore` / `pointsLive` also coerce nested `{ points | pts | score | liveScore | pointsLive | live }` the same way Sleeper chips do, including playerId-to-points maps and roster `entries` keyed by player id.

## ESPN: hidden vs API

| Channel | Auth | Use |
| --- | --- | --- |
| `lm-api-reads.fantasy.espn.com` v3 league views | `espn_s2` + `SWID` for private leagues | **Canonical fantasy path** (already in `espnClient`) |

| `cdn.espn.com/core/nfl/scoreboard?xhr=1` | none | Same scoreboard, CDN. Fallback only. |
| ESPN FantasyCast / site WebSocket | n/a | **No public fantasy websocket.** FantasyCast polls the v3 JSON views. Re-checked 2026-08-30: Hubitat, cwendt94/`espn-api`, and recent reverse-engineering writeups still poll `lm-api-reads` `mLiveScoring`. ESPN's own fan-scale push (Azure Web PubSub / GraphQL) is not a client-usable fantasy feed. |
| `kona_player_info` + filter | cookies | Free-agent / projection pool. Not needed for the HUD matchup. |
| `kona_league_communication` | cookies | Activity feed. Alternative to `mTransactions2` later. |

Known views (non-exhaustive): `mTeam`, `mRoster`, `mMatchup`, `mMatchupScore`, `mLiveScoring`, `mBoxscore`, `mScoreboard`, `mSettings`, `mStatus`, `mTransactions2`, `mSchedule`, `mStandings`, `kona_player_info`. Combining views is not additive — live polls should request a **small live set**, not the bootstrap dump.

cwendt94/`espn-api` live box scores use `view=mMatchupScore,mScoreboard` + `scoringPeriodId` + `X-Fantasy-Filter` `{ schedule: { filterMatchupPeriodIds: { value: [week] } } }`. That is the payload that carries `rosterForCurrentScoringPeriod` and `totalPointsLive`. We were requesting seven views with no week filter, so every poll pulled the full season schedule plus settings. Team totals prefer a **positive** compact live field (`totalPointsLive` / `liveScore` / `pointsLive`) over leftover starter week actuals, leftover `pointsByScoringPeriod` / `totalPoints` / schedule `liveScore`, so a merged boxscore cannot roll a compact correction back up. Explicit compact team `liveScore` / `appliedActiveReal` of **0** also wins over leftover schedule `liveScore` / `totalPointsLive` / week actuals (a reversal); a zeroed `totalPointsLive` stub alone does not. Positive compact starter chips also win over leftover `pointsByScoringPeriod` **and leftover `totalPointsLive`** when the compact team row omits `liveScore`. Compact `appliedTotal` chips count the same way when `liveScore` is omitted, so leftover week actuals cannot freeze HUD behind a scorer-only `mLiveScoring` blob that only ships `appliedTotal`. When those live fields are missing and starter chips are still zero, week actuals and finals still fill. `totalProjectedPointsLive` is ignored.

Live stats in the adapter stay `statSourceId === 0 && statSplitTypeId === 1` (actuals, current split). Player `stats` may be an **array, a keyed map, or a single stat object**, on `player.stats`, `playerPoolEntry.stats`, or the compact row, so a live blob cannot hide week actuals. Nested `playerPoolEntry` `liveScore` / `totalPointsLive` / `appliedActiveReal` / `points` count as live even when leftover week projections sit on `player.stats`, so the full boxscore parse path cannot freeze starter chips. When a week actual is present **and** a compact live field is higher, the live value wins so a stale `appliedTotal` cannot freeze chips behind `mLiveScoring`. A **positive** live field also wins when leftover week actual is higher, so a deferred `mMatchupScore` SWR cannot roll a compact correction back up. Explicit compact `liveScore` / `appliedActiveReal` of **0** also wins over leftover week actuals and leftover `points` (a reversal); a zeroed `totalPointsLive` stub alone does not, so pre-kickoff schedule zeros cannot wipe chips. Totals and ids coerce **finite numeric strings** the same way the NFL scoreboard parser does, so a quoted JSON number cannot freeze the HUD at last poll's score. When a live tick injects an unscoped actual next to a leftover week actual, the **unscoped compact value wins** even when it is lower, so leftover `scoringPeriodId` actuals cannot freeze starter chips behind scorer-only `appliedTotal`. `appliedStatTotal` is only a fallback when that week has no projection-only stats — otherwise a season total or leftover `appliedStatTotal` would paint as live points. Overlay merges player `stats` by source/split/period and keeps the compact `appliedTotal` when that field is present (including `0`) so leftover week actuals cannot freeze a reversal; keys only on leftover stay. Team `pointsByScoringPeriod` and roster `appliedStatTotal` overlay the same way. Team totals prefer `max(totalPointsLive, liveScore)` so a compact row that ships `totalPointsLive: 0` next to a filled `liveScore` cannot freeze the HUD; `points` / compact team fields stay a fallback when those live fields are missing or still zero. The same max applies per player (`totalPointsLive` / `liveScore` / `appliedActiveReal`) so a zeroed live total cannot hide the compact chip. Compact player rows also read `appliedTotal` when `liveScore` / `totalPointsLive` / stats are omitted. Compact player `points` and `appliedActiveReal` count as live even when leftover week projections sit on the same row, including when those live fields are nested on `playerPoolEntry` (boxscore shape). Compact team rows without a roster also read `appliedActiveReal` / `appliedTotal` / `appliedStatTotal` / `points` so a live blob that omits `liveScore` and `players` can still move the HUD total. An empty compact `players: []` still counts as chips present, so a season `points` / `appliedTotal` cannot paint as live. SWID identity matches `owners` as strings or `{id}` objects so a private league cannot bind `filterTeamIds` / HUD to `teams[0]`. When owners are present and SWID matches none of them, identity is left unmatched instead of silently using `teams[0]`. `totalProjectedPointsLive` is ignored. Bench actuals are not added to the team total. `lineupSlotId` and `defaultPositionId` coerce quoted JSON numbers so a string `"20"` cannot sit in the starter set and inflate that total. Compact `mLiveScoring` overlay matches last HUD `myTeam.id` / `oppTeam.id` with the same `num()` coerce so a quoted team id cannot miss the live blob. Week roster entries are read from `rosterForCurrentScoringPeriod` **or** `rosterForMatchupPeriod` (espn-api boxscore key); season `teams[].roster` is not used for live points.

## Sleeper: official HTTP only

[docs.sleeper.com](https://docs.sleeper.com/) is the contract:

- Stay under **1000 req/min** (IP block risk).
- `/players/nfl` is huge — **at most once per day** (we already disk-cache 24h).
- Live points come from `GET /league/{id}/matchups/{week}` (`points`, `players_points`, `starters_points`). A matchup total also coerces `pts` / `live_points` / `liveScore` / `pointsLive`, and nested chip objects also read `pointsLive` / `live`. `player_points` / `starter_points` fill `players_points` / `starters_points` when the official keys are omitted. Starter/player id lists also coerce `{ player_id | playerId | id }` objects; a list of objects that cannot be coerced is treated as omitted so overlay cannot paint an empty lineup. There is **no official websocket** for scoring. Team totals prefer `max(points, starter players_points)` so a lagging `points` field cannot hide live starter actuals. Overlay onto last HUD **trusts** a `/matchups` payload that includes a **positive** `players_points` / `starters_points` chip, a positive `points` total, or commissioner `custom_points` (including `0`) so a stat correction can move chips down; a zeroed stub — including `players_points` / `starters_points` all `0` — still cannot wipe last scores, including when the other roster in the same `/matchups` payload is live. A team total with all-zero player maps still cannot wipe last starter chips. Per-player chips prefer a **positive** `players_points` over `starters_points` so a lagging starter array cannot freeze a correction; a zeroed `players_points` map still falls through to `starters_points` so it cannot hide the parallel starter array. `/matchups` and `/rosters` coerce quoted or numeric `points` / `custom_points` / starter player ids / `players_points` values so a typed JSON number cannot miss overlay or rebuild. Array `players_points` zip onto `players` when lengths match, otherwise onto `starters`, and index-keyed `starters_points` objects become the parallel array only for a dense `0..n-1` index (player-id keys align onto `starters` instead), so a typed JSON array cannot drop Sunday chips or wipe last HUD with a sparse index list. Dense `0..n-1` `starters` / `players` objects coerce the same way so a typed JSON roster cannot lose lineup ids. A player-id keyed `{ "4046": true }` set becomes that id list instead of dropping, and is not treated as a sparse index of length 4046. A player-id keyed `starters_points` object with **no** `starters` list still merges into `players_points` so last HUD chips can move by id. Nested chip values `{ points | pts | score | liveScore }` coerce the same way as a bare number so a typed JSON wrapper cannot drop Sunday chips. An array of `{ player_id, points }` rows keys chips by that id instead of zipping roster order, and the same rows on `starters_points` align onto `starters` by id. Transaction `adds` / `drops` arrays of `{ player_id, roster_id }` coerce onto the same map as the official object form so tape names cannot miss a typed JSON list. Overlay and rebuild coerce quoted JSON `roster_id` / `matchup_id` / starter player ids so a string id cannot skip last-HUD overlay and hitch on a roster-disk parse. Commissioner `custom_points` still wins when it is a number. Cloudflare on that host sends **`s-maxage=300`** on matchups, transactions, league lists, and rosters (probed 2026-08-31: `/state/nfl` HIT age 9–49 with `s-maxage=60`; `Cache-Control: no-cache` request header still HIT; a `?_=` query is a MISS). Live `/matchups` appends `?_=` keyed to the 3s poll bucket. Transactions, `GET /leagues`, `/rosters`, `/users`, `/user/{username}`, and `/state/nfl` bust on their local TTL buckets (30s / 5 min / 120s / 60s) so a connect, roster SWR, username lookup, or Tuesday week rollover cannot paint a CDN HIT. `/user/{username}` is `s-maxage=120` (probed 2026-08-31). `/state/nfl` `s-maxage=60` matches the local SWR, but a HIT still serves the previous week until origin is busted.
- Undocumented `stats/nfl/{season}/{week}` and `projections/nfl/{season}/{week}` exist in community clients. Do **not** use them for live HUD totals — matchups are the league-scoring source of truth. Flag only: injury text on Sleeper is from the daily player map, so IR/OUT can lag until the next day's cache. ESPN roster `injuryStatus` is per-poll.

Harden every Sleeper GET: timeout, 429 backoff (honors `Retry-After` when it fits the fetch timeout), typed status errors. Every official GET except the daily `/players/nfl` dump now **defaults its own Cloudflare `?_=` bust** (matchups 3s, transactions 30s, `/state/nfl` 60s, `/user` 120s, leagues/rosters/users 5 min) so a missed poller override cannot freeze Sunday scores on a 5-minute HIT. `/state/nfl` coerces integer and string `week` / `display_week` / season fields the same way live points do. A thin `/state/nfl` body that omits `display_week`, `league_season`, or `season_type` still parses (`display_week` from `week`, `league_season` from `season`, `season_type` `regular`) so a shape change cannot stall `/matchups` on a stale week. Wrapped `{ data|payload|state|nfl|user|matchup|roster|league|transaction: { … } }` envelopes unwrap the same way list GETs do. Transaction `adds` / `drops` maps also coerce nested `{ roster_id }` / `{ player_id, roster_id }` values. Disk NFL snapshots fill the same gaps. League rows that omit `name` still keep the board (`league_id` as the label). List GETs unwrap `{ matchups|rosters|users|leagues|transactions|data|results|items|payload }` envelopes so a wrapped `/matchups` body cannot paint empty HUD. Index-keyed `{ "0": { roster_id } }` maps and wrap keys that hold those maps unwrap the same way. Singular `{ matchup: [] }` / `{ roster: [] }` list keys unwrap too. Nested chip objects also read `fpts` / `fp`. Top-level matchup `fpts` / `fp` fill `points` when `points` is omitted. A list body that is a single matchup/roster/user/league/transaction object becomes a one-row list. An empty or invalid JSON list body is `[]` so a truncated Cloudflare 200 cannot throw out of Sunday `/matchups`. Matchup `points` / `custom_points` coerce nested `{ points | pts | score | liveScore }` the same way starter chips do, so a typed JSON object cannot drop the HUD team total. `GET /user`, `/league`, `/rosters`, `/users`, `/matchups`, and `/transactions` coerce quoted or numeric `user_id` / `league_id` / `roster_id` / `transaction_id` the same way so a typed JSON number cannot miss HUD identity or drop tape rows. Transaction `adds` / `drops` coerce quoted player-id keys and roster-id values so tape names cannot miss a typed JSON map. Roster `settings.wins` / `losses` / `ties` coerce quoted integers so a LEAGUES record cannot show `"5"-"2"`. League-user `metadata.team_name` and `display_name` coerce the same way so a LEAGUES card cannot miss its name. Roster disk hydrate accepts string or number ids instead of dropping the snapshot. Adapter owner matching compares `String(user_id)` to `String(owner_id)`. League-scoped GETs require a **numeric id** (replay slugs never hit the network). A blank username does not call `GET /user/`. List endpoints coerce a non-array 200 body to `[]` so a junk payload cannot throw out of the HUD, and unwrap `{ matchups | rosters | users | leagues | transactions | data | results }` when that wrapper is the only list so a typed JSON envelope cannot drop Sunday `/matchups`. `/state/nfl` must include `week`, `display_week`, `season`, `league_season`, and `season_type` or the fetch is treated as failed. If that fetch fails and there is no disk snapshot, the poller uses a **calendar NFL fallback** (season year; week 1) so ESPN scoring is not blocked on Sleeper being up — last-HUD week is preferred when present. On a **cold start with no disk**, that calendar seed is used **immediately** at warmup so `sideline-matchups.json` can hydrate `myTeam.id` before the first rest ESPN GET (week-wide ~219KB vs `filterTeamIds` ~45KB); `GET /state/nfl` SWR starts **after** the HUD scoring GET returns so it cannot starve `mLiveScoring` / `/matchups`. A week/season shift still re-kicks the selected HUD the same tick. The calendar seed is **not** written to disk. Cache rosters + users (stable during Sunday). Always refetch matchups. ESPN league GETs also require a numeric id.

## Latency / timing (what was wrong)

`refresh()` was one sequential pass:

1. NFL state
2. Sleeper leagues
3. ESPN fan probe + **per-league settings fetch**
4. **Per-league matchup fetch, awaited in a `for` loop** (Sleeper: 3 calls each)
5. Per selected/pinned transactions

Then `schedule()` waited **10s/30s after the refresh finished**. If a cycle took 8s, scores aged ~18s. ESPN leagues were fetched twice (discovery views, then full matchup views). Calendar live window missed London (Sun ~9:30a ET), Saturday slates, Friday internationals, and Thanksgiving 12:30p (Thursday live started at 7:30p ET).

## Implementation (this slice)

1. Shared `fetchJson`: **5s timeout, no retry** by default. An empty JSON 200 is `null` (not Invalid JSON) so a truncated Cloudflare/CloudFront body cannot throw on the live path. ESPN compact `null` is a miss (`compactHit` false) so cookie retry still runs; Sleeper list GETs already map that to `[]`. Selected HUD `mLiveScoring` / `/matchups` abort at the **3s live poll** so a hung GET cannot pile into the next tick. Rest/pinned compact also abort at **3s while games are live** (or the calendar gameday window) so hung pinned GETs cannot occupy the pipe past the next HUD tick; idle rest stays 5s. Rest Sleeper `/rosters`+`/users` and rest `GET /user` use that same 3s live abort (cold HUD identity already did). Rest ESPN `mMatchupScore` recover also abort at **3s while live** at Chromium **low**; selected HUD recover stays **high**. Deferred `mMatchupScore` SWR, waiver tape, roster SWR, and after-score ESPN `mTeam` use the same 3s live abort (still Chromium **low**) so they cannot occupy the rest pool past the next HUD tick. Discovery (`fan.api`, `mSettings`/`mTeam`), Sleeper `GET /leagues`, and `GET /user` SWR also abort at **3s** so a Sunday connect cannot occupy a connection past the next HUD tick. Compact `mLiveScoring` and Sleeper `/matchups` for the **selected HUD** pass Chromium fetch **`priority: 'high'`** through Electron **`net.fetch`** (not Node's `global fetch` / undici, which ignores priority); rest/pinned compact scoring is **`low` while games are live** (or the calendar gameday window) so pinned `mLiveScoring` / `/matchups` cannot occupy HTTP/2 over the next 3s selected GET; idle rest stays default. Rest Sleeper `/rosters`+`/users` and `GET /user` are also **`low` while live** (cold HUD identity already was) so they cannot occupy `api.sleeper.app` HTTP/2 over HUD `/matchups`; idle rest identity stays default. The 251KB NFL scoreboard uses **`priority: 'low'`** so a background download cannot starve scoring. ESPN league GETs use **`persist:espn` `session.fetch`** (Chromium stack, login partition) **and still send the decoded `Cookie` header**. `lm-api-reads.fantasy.espn.com` is not guaranteed to receive `.espn.com` cookies from the jar, so a header-less session GET would 401 every private tick. Cookie IPC still supplies SWID for identity. Inflight coalescing keys on timeout, retries, **and priority**, so a high live GET does not join a low in-flight. A 200 `text/html` body or invalid JSON is an `HttpError` and is **not** retried (CloudFront error pages used to look like a timeout and burn a second attempt). Explicit `retries: 1` still retries 429/5xx. A 429 `Retry-After` that fits the fetch timeout is honored instead of the 1.5s default; a longer wait throws so the next 3s poll is the retry. ESPN and Sleeper clients default to that same live budget so a missed poller override cannot hold a tick behind 8s+retry. `/players/nfl` still uses 30s / 0 retries.
2. ESPN live views: `mMatchupScore` + `mLiveScoring` + week `X-Fantasy-Filter`. Probed 2026-08-30 on public `899513` week 1: `mScoreboard` is **~287KB** and duplicates the current-week roster already on `mMatchupScore`; combining all three views was ~321KB vs **~218KB** without `mScoreboard`. Adding `schedule.filterTeamIds` for the user's team (from cached `mTeam` / SWID, with quoted or numeric `id`) cut that further to **~45KB / 1 game / 69ms** vs 219KB / 5 games / 146ms. `teams.filterIds` and `schedule.limit` are **400**. A cold tick with no identity cache **and no last `myTeam.id`** still uses the week-only filter and does **not** parse ESPN teams disk before `mLiveScoring`; `mTeam` starts **after** the scoring GET returns so it cannot starve `mLiveScoring` / `mMatchupScore`. Live ticks skip that after-score `mTeam` when last HUD already has `myTeam.id` (`filterTeamIds` already works); idle still hydrates owners. In-flight `mTeam` is keyed by league id plus cookie auth so a public identity GET cannot satisfy a private SWID fetch. After compact `mLiveScoring` paints, `mMatchupScore` SWR is **deferred until after rest-of-board scoring and transactions** (`pendingEspnFullSwr`, same drain as Sleeper roster SWR) so a ~40KB boxscore refresh cannot share the pipe with the next 3s live GET. While NFL games are `in`, that deferred SWR is **skipped** (lineup is locked; compact live is the score path); HUD recover still runs immediately if compact fails or there is no overlay. Calendar-live Sunday morning still defers so lineup can SWR before lock. If compact `mLiveScoring` **fails**, that boxscore starts **immediately** at `priority: 'high'` (not after rest/tx) and paints through the same overlay-max path so a stale boxscore cannot roll last HUD totals back. In-flight recover is keyed by league, week, cookie auth, HUD vs rest, and `filterTeamIds`, so a public 401 cannot satisfy a cookie HUD recover. A cookie retry of compact live increments the fetch generation so a late public recover cannot paint over the authenticated HUD. That deferred payload is overlaid onto last HUD with `max` live totals; if it has no live rows, the screen is left alone so a stale boxscore cannot roll scores back. Last scores in `matchupCache` supply `myTeam.id` for rest ESPN boards even when they are not the selected HUD, so those GETs use `filterTeamIds` and skip `mTeam` on the scoring GET (owners SWR after that payload). `mScoreboard` is also the only live view that ships `teams[]`, but those teams omit `primaryOwner` — identity stays on cached `mTeam`. `mLiveScoring` alone is ~858B until games are `in`. We still do **not** send `mBoxscore`. `LIVE_VIEWS` is the same score-only set as `SCORE_VIEWS` (`mMatchupScore` + `mLiveScoring`, no `mTeam`). The unused 7-view `MATCHUP_VIEWS` dump is gone so a live fetch cannot request `mRoster`/`mMatchup`/`mSettings`/`mStatus` beside scoring. Discovery views stay slow-path and TTL-cached. After owners are cached (memory, and disk for 7 days), ticks omit `mTeam`. ESPN HUD scoring kicks `mLiveScoring` **before** parsing `sideline-espn-scores.json` / teams disk when last HUD already has `myTeam.id`; boxscore disk hydrate runs **after** that GET returns so overlay can re-read the cache, and lineup boxscore that lands during the RTT is used instead of overlaying onto last starter rows.
3. Sleeper: timeout/429; cache rosters/users; matchups every tick; `Promise.allSettled` across leagues. The Sleeper client **defaults** to a **5s timeout and no retry** on every official GET except `/players/nfl` (30s / 0). The next 3s poll is the retry. Connect-time `getUser` uses that same live budget. ESPN `lm-api-reads` / `fan.api` default to the same 5s live budget so a cold identity fetch cannot hold the HUD behind 8s+retry. After selected HUD scores publish, the next poll is **scheduled immediately and `inFlight` is released**; discovery, rest-of-board, and transaction fetches continue in the background so a slow waiver feed or `fan.api` cannot delay the next scoring tick. Re-probed 2026-08-31: `GET /league/{id}/matchups/{week}` is Cloudflare **`s-maxage=300`** (5 min). Live `/matchups` **must** keep `?_=` on the 3s bucket or Sunday scores freeze on a CDN HIT. The Sleeper client now defaults that bust even when the poller omits `cacheBust`. `GET /v1/stats/nfl/regular/2026/1` is 200 **2B** / `s-maxage=30` until week 1 games — do not poll it beside scoring.
4. Next poll delay = `max(0, interval - elapsed)` so live scoring is **3s start-to-start**. ESPN `lm-api-reads` `mLiveScoring` re-probed 2026-08-31: `Cache-Control: must-revalidate`, `Expires: -1`, `Pragma: no-cache`, CloudFront **MISS** — there is no CDN `max-age=3` floor on the live view anymore, so 3s is our interval, not a cache cap. Do not drop below 3s until an in-progress Sunday proves the blob actually changes faster. Idle stays 30s. Overlap guard. A scoreboard of all `pre` must not reschedule that 30s over an armed 3s gameday tick (`scoreboardPollLive` ORs calendar live). Rest settle skips a second `schedule()` when HUD already armed the next tick, unless games just went `in` and the armed interval was idle. The public NFL scoreboard (~251KB) is **cached 10s while any game is `in`** so a 3s scoring tick does not re-download it (site.web.api `Cache-Control` was `max-age=2` then `max-age=3` on back-to-back probes; origin is now `max-age=10`). While the slate is still `pre`/`post`, that cache is the **30s idle poll** so a Sunday 9am calendar-live window cannot occupy the rest pool with 251KB every 10s before kickoff; ticker clocks stay off until a game is `in`. A cache hit also skips the ticker broadcast when live/ticker are unchanged. Sequential scoreboard hosts use a **2s timeout** (probed ~193ms) instead of 5s×3, so a hung first host fails over before the next scoring tick. The last host that returned 200 is tried **first on the next download**, so a dead `site.web.api` cannot spend 2s on every 10s cache miss. While games are live and a last-good host or ticker cache exists, a failed scoreboard GET does **not** walk the remaining hosts (another 2s×2 of ~251KB) — keep last ticker until the next 10s miss. When last HUD is already on screen, that 251KB download waits until the selected scoring GET **returns**. Idle ticks also wait until **pinned** rest scoring **finishes** so it cannot starve `mLiveScoring` / `/matchups`. Gameday ticks (`liveTick`, calendar or games `in`) start it **after HUD** (still Chromium **low**) even on a Sunday open before `pollingLive` is set, and do **not** wait on rest prefetch / pinned LEAGUES GETs **or** league-list / cookie IPC so games-in detection and ticker clocks cannot sit behind pinned boards. Cold LEAGUES boards (30s TTL) start after pinned scoring **and** selected/pinned transactions so they do not hold live detection, the overlay ticker, or the waiver tape. On a 3s tick the TX cache is usually fresh, so cold boards start immediately after pinned. ~20 live ticks/min × selected + pinned matchup GETs stays well under Sleeper's 1000 req/min.
5. Live = NFL games with `status.type.state === 'in'` (or header-API `status: "in"`). Calendar is fallback only when every scoreboard host fails — a Sunday with every game `pre` stays idle. `site.api.espn.com` scoreboard/injuries started returning **403 Access Denied** from this network on 2026-08-30. Live detection tries `site.web.api.espn.com` v2 scoreboard first (same JSON as `site.api`, **200**), then the header API, then `site.api` last. Hitting `site.api` first wasted a 403 RTT on every live tick. `cdn.espn.com/core/nfl/scoreboard?xhr=1` returned HTTP 202 empty body. Re-probed 2026-08-30 22:45 CT: both `site.api` and `site.web.api` `/injuries` are **HTTP 200 ~8.8MB / 0.5s**. Polling that on a 10s live tick would starve ESPN/Sleeper scoring, so the poller does not fetch it.
